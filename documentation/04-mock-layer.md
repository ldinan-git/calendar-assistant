# The mock layer (`/responses`)

## Why

The real thing is an LLM. For a class demo that has to run offline, deterministically, with no API key, every LLM response is a hardcoded JSON file. The app doesn't know the difference: all LLM access goes through one function.

```js
callLLM(task, input)  // task: "extract" | "analyze" | "parse" | "rank" | "advice"
```

`VITE_LLM_MODE=mock` (default) resolves the answer from `/responses`. `VITE_LLM_MODE=live` sends the same input to the Anthropic API with the prompt from `src/api/prompts.js`.

Every call, in either mode, is recorded in a trace: task, input, output, which file answered, latency. The Summary tab renders it.

## How a file is chosen

`responses/manifest.json`:

```
tags      regexes run over the taught facts (as text) to answer "which facts exist?"
extract   rules: first regex that matches the user's sentence wins; else fallback file
parse     rules: first regex that matches the request text wins; else fallback file
analyze   the set of relevant tags (jake, josh) picks one of 4 files
rank      rules: regex on request text AND all requireTags present; else null (no fixture)
advice    rules: regex on invite title AND all requireTags present; else fallback file
```

Rules are ordered most-specific-first. Example, Jake request with all facts taught:

```json
{ "match": "45 minutes with jake", "requireTags": ["jake","josh","early"], "file": "rank/jake45_full.json" },
{ "match": "45 minutes with jake", "requireTags": ["jake","josh"],         "file": "rank/jake45_partner_flexible.json" },
{ "match": "45 minutes with jake",                                        "file": "rank/jake45_generic.json" }
```

The three files differ because the *reasoning text* cites taught facts. A response that says "Jake is a partner" is wrong if the user never taught that. So each fixture is only served when the facts it mentions exist.

## Fixture inventory

| Folder | Files | Notes |
|---|---|---|
| `extract/` | `jake_partner`, `josh_flexible`, `flight_buffer`, `no_early_meetings`, `_fallback` | Fallback saves an `other` fact echoing the user's text |
| `parse/` | `jake_45`, `priya_josh_thursday_30`, `roadmap_sync_60`, `quick_sync_30`, `_fallback` | Last two are for "Find another time" after an incoming invite |
| `analyze/` | `base`, `jake`, `josh`, `jake_josh` | Generated by `scripts/gen-analyze-fixtures.mjs` |
| `rank/` | `jake45_full`, `jake45_partner_flexible`, `jake45_generic`, `priya_josh_thursday`, `roadmap_sync`, `quick_sync` | Reference slots by `{day, start}` |
| `advice/` | `roadmap_sync_flight`, `roadmap_sync_plain`, `quick_sync_jake`, `quick_sync_plain`, `_fallback` | |

Response shapes are the same ones the live prompts ask for. If a prompt changes shape, the fixtures must change too, and `npm run check:flow` will probably catch it.

## One deliberate difference from live mode: slot references

The live `rank` prompt asks for `candidate_id` ("c3"). Fixtures can't know candidate ids ahead of time, because they depend on which facts are taught and what the code generated. So fixtures use `"slot": { "day": 0, "start": 720 }`, and `matchRankedOptions()` accepts either form. A nice side effect: it makes the "LLM can only choose among slots code verified" guardrail visible, because a fixture slot that isn't a valid candidate is silently dropped.

## Known limits (honest list)

1. **Fixture explosion.** Reasoning text depends on which facts exist, so the number of rank files grows with the number of fact combinations. Three is manageable, ten isn't. The `analyze` call dodges this by only keying on the two tags that change ratings.
2. **Hardcoded details inside fixtures.** `jake45_full.json` has a `bump_message` that says "move our 1:1 to Monday at 10:30 AM". That time is where `findReplacement` puts it *today*. If the calendar changes, the message and the real new slot can disagree. `check:flow` asserts they match for the demo calendar.
3. **New events are unrated.** After you send an invite, the new event isn't in any `analyze` fixture, so it renders gray until live mode.
4. **Anything off-script falls back.** Unknown teach sentence: saved as plain note. Unknown meeting request: parse defaults to 30 minutes with nobody, and rank has no fixture so the app uses code ordering with a generic reason. The fallback path is deliberate (it's what happens if a live call fails too).
5. **The matcher is a tiny fake NLU.** Regexes on the user's text pretending to be an LLM. It's fine for a demo and it's obviously not the product.
6. **Tag detection is regex over JSON text.** `jake.*partner` would also match a fact that says "Jake is not a partner". Fine for fixtures, not something to reuse.

## Adding a fixture

1. Add `responses/<task>/<name>.json` in the same shape the prompt asks for.
2. Add a rule to `manifest.json` (most specific first).
3. For `rank`, run `npm run check` to see real candidate slots, and reference ones that appear in the list.
4. `npm run check:flow` to confirm it resolves.

## Idea: record/replay

Instead of hand-authoring fixtures, run in live mode once and write each response to `/responses` automatically (key = hash of task + input). Then mock mode is a recording of real model behavior. See `07-ideas-backlog.md`.
